# FIRERPA SSH Investigation — Resolved

**Issue:** https://github.com/firerpa/lamda/issues/145
**Date:** 2026-07-13
**Status:** Resolved and deployed on s24 + p7a
**Goal:** Use FIRERPA SSH on non-root Android as an authenticated backup repair channel.

## Resolution

Inbound SSH works on a non-root device. Four details caused the original failures:

1. The SSH username is `shell`, not `root`, when FIRERPA runs as Android UID 2000.
2. The default private key embedded by upstream `tools/ssh.sh` matches FIRERPA's default
   authorized key. The separate upstream `tools/test.pem` does not match in v10.0.
3. A custom certificate is enabled with the explicit server option
   `--certificate=/path/to/lamda.pem`. Merely placing `lamda.pem` beside
   `properties.local` does not select it in the manual server-tarball deployment.
4. The PKCS#1 key emitted by upstream `tools/cert.py` is valid. PKCS#8 conversion is not
   required.
5. FIRERPA v10.0's bundled UI helper called Android `getUiAutomation(0)`, which suppresses
   ordinary accessibility services. The stayturgid role deterministically patches that DEX
   call to flag `1` (`FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`). Because FIRERPA validates
   the signed JAR at startup, its lifecycle controller starts with the signed original,
   waits for integrity validation and listeners, atomically swaps in the patched JAR, then
   restarts only the UI helper processes.

The durable stayturgid configuration now uses a private custom service certificate:

- Mac certificate: `~/.config/stayturgid/firerpa.pem` (mode 0600)
- Device certificate: `/data/local/tmp/firerpa/server/lamda.pem` (mode 0600, shell-owned)
- Server launch: `bin/launch.sh --port=65000 --certificate=.../lamda.pem`
- SSH alias: `ssh s24-firerpa` (Tailscale IP, port 65000, user `shell`)
- gRPC clients fail closed if the configured certificate is missing
- Unauthenticated gRPC and the upstream default SSH identity are rejected
- AutoJs6, AutoInput, and Octoclip remain bound while secure FIRERPA UI automation works

## Verified Tests on s24 + p7a

### Default certificate behavior

- Device authorized-key fingerprint:
  `SHA256:4204fd8OU5UhXVnK800CW4vZttzOWOXBE7wHDatNRTc`
- The private identity embedded by upstream `tools/ssh.sh` has the same fingerprint.
- `tools/test.pem` has a different fingerprint and is not the v10.0 default SSH identity.
- Using the embedded identity with `shell@<tailscale-ip>:65000` succeeded.

This explains why the initial `test.pem` attempt failed without implying that inbound SSH
was unsupported.

### Custom certificate behavior

A custom certificate generated by upstream `tools/cert.py` was started with the explicit
`--certificate` option. The resulting device authorized key matched the custom private key.
The following all passed:

- `ssh s24-firerpa 'id'` and `ssh p7a-firerpa 'id'` returned UID 2000 (`shell`)
- authenticated `lamda.client.Device(..., certificate=...)` returned FIRERPA v10.0 on both
- a gRPC client without the custom certificate was rejected
- the upstream default SSH identity was rejected
- authenticated UI hierarchy capture succeeded on both devices
- `dumpsys accessibility` showed AutoJs6, AutoInput, and Octoclip bound concurrently

### Clean reboot behavior

FIRERPA's server archive must run as Android's `shell` identity. A Termux app process cannot
directly start it after a reboot. The Python Termux supervisor first uses privileged
localhost ADB on port 5555. If that bridge is absent but Shizuku and Termux's persistent
authorization are available, it uses `rish` only to set `service.adb.tcp.port=5555` and
restart adbd, waits for localhost ADB to return as UID 2000, and launches FIRERPA there.
Directly backgrounding FIRERPA in a `rish` command is not durable: the binder session owns
and kills its child even with `nohup`/`setsid`.

The S24 reboot and subsequent controlled stop/start validated automatic localhost-ADB
recovery and the full signed-start/patched-swap lifecycle. This is still a bootstrapping
limitation, not an SSH limitation: until a UID-2000 bridge exists, non-root Termux cannot
start the server archive. Once running, FIRERPA is an independent repair channel.

The reboot also exposed two supervisor bugs that are now fixed in Python:

- repair/API timeouts no longer terminate the daemon loop;
- the forked daemon closes the Termux:Boot launch pipe and detaches cleanly.

## Operator Commands

```bash
# Deploy/redeploy the certificate-authenticated service
make firerpa-deploy HOSTS=s24,p7a

# Validate both transports
ssh s24-firerpa 'id'
ssh p7a-firerpa 'id'
make firerpa-heal HOSTS=s24,p7a
make firerpa-health

# Inspect the on-device supervisor's decisions
ssh s24 'tail -n 100 ~/.stayturgid/logs/boot.log'
```

For a deployment outside stayturgid, use the self-documenting
[`examples/firerpa-nonroot/justfile`](../../examples/firerpa-nonroot/justfile) and
[standalone guide](../../examples/firerpa-nonroot/README.md). They download and verify
upstream v10.0, generate a private certificate, install the Python client, build the
hash-pinned accessibility patch, deploy over an arbitrary UID-2000 ADB target, and run
the same signed-start/patched-swap lifecycle used by the fleet. The guide includes all
manual command equivalents, reboot/`rish` recovery, security notes, and troubleshooting.

If a handset reboot leaves both localhost ADB and Shizuku down, restore one privileged bridge
using the normal stayturgid recovery path (USB ADB, wireless debugging/Shizuku, or the
AutoJs6 catastrophic recovery). The Python supervisor will then start FIRERPA on its next
attempt. On both phones, open Shizuku's Termux authorization and choose **Allow all the
time**. Those grants were validated on 2026-07-13: `rish` returned UID 2000 and successfully
restored the privileged localhost adbd path used to launch FIRERPA; secure SSH returned UID
2000 afterward. Dashboard detection and an immediate authorization/test action remain H8.
